# 从需求到 GitHub

产物是用户能打开、配置和使用的产品，以及别人能接手的源码和简短说明。保存需求、选择依据与验证证据；不把完整聊天当开发文档。

## 先复用，再搭建

浏览当前可用 skill 目录、本机存在的 `SKILL_CATALOG.md`、项目约定和模块注册表；只读命中的完整 skill 与目标代码。不要扫描其他项目的客户资料。已有功能用当前实现；接手半成品需要拆模块时，可调用可用的 `modularize-project`，不强行安装它。网站、桌面、凭据配置等采用当前环境适合的工具与官方文档，不把此案例的技术栈套到所有项目。

## 把原话变成可验收的需求

沿用项目已有需求/状态文件；没有时按需复制 [需求模板](assets/PROJECT_BRIEF.md) 和 [接续模板](assets/PROJECT_STATE.md)。记录谁使用、提供什么、怎样操作、得到什么、在哪运行、验收证据。需求、合理假设与尚未接通的能力分开。复述真正影响实现的选择；能从现有信息确定的继续做，只有阻断实现的问题才询问。

特别确认：交付是 skill、桌面程序还是独立云端；手机能打开不等于电脑关机后可用；共享源码不等于共享模型、私有资料或已登录会话。涉及这些选择时读 [运行与迁移](references/delivery-modes.md)。

## 实现一条完整路径

先让用户输入经过真实处理，产生可查看、保存的输出，再补本轮要求的模块。沿用原框架和依赖锁；确定性操作用代码，不为每个步骤增加模型调用。把开发分工与产品运行时 Agent 分开。

按职责记录入口、输入输出、依赖和检查方法，不规定模块数量。能并行时委派边界清楚的任务，传递相关 skill 路径与允许修改范围，避免共同改同一文件。新成员只读短状态、目标模块和受影响调用方。共享接口变化才扩大读取和回归。

## 验收并修到本轮目标成立

验证用户操作链和失败恢复，不只看按钮是否存在。构建、mock、真实接口、界面、收费模型、外部系统分别标记；记录对应版本、命令/证据和结果。新失败先修根因并检查受影响路径；检查已通过且实现未变时，不重复全量测试。

私有数据、多用户隔离、文件版本和凭据保存等边界按实际产品检查。缺少外部凭据、权限或运行能力时，完成独立部分并记录准确缺口；不把 mock 通过写成真实接通，不绕过 MFA，也不无休止重试外部故障。实际视觉操作不可用时明确界面未实测。

## 交付与后续接手

发布或迁移时才读 [GitHub 与打包](references/github-release.md)。源码、便携程序、skill 包和运行数据分别交付；公开文件使用显式清单并核对哈希。保留用户当前授权范围，不因使用本 skill 重复索要已经给出的许可，也不从历史发布推断新项目的发布权限。

交付前更新短状态和模块入口：需求对应的实际功能、当前源码/版本、测试、未验证项、下一步。写人能读懂的说明：用户提供什么、工具完成什么、怎样用；语言按用户要求。新增或修改 skill 后同步当前环境的技能索引。

需要了解此方法从哪里来时再读 [课程平台案例](references/campus-example.md)。默认不读取案例、全部参考、生成 bundle 或历史日志。不承诺未经测量的 token 节省比例。
